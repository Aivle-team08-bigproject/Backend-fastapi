# 공지사항 DB 피드백 수용 설계

## 기준

- 피드백 원문: `NOTICES_DB_회신.md` (DB 담당, 2026-08-09)
- 대상 브랜치: `feature/notices-backend-reapply`
- 기준 Alembic head: `3f8e1c2a7b90`
- 현재 브랜치 상태: 공지사항 API·모델은 존재하지만 Alembic revision은 제거된 상태

## 결정

DB 담당 피드백을 수용한다. `service.notices`는 수동 SQL이 아니라 Alembic revision으로 관리하며, 수동 적용 SQL은 PR에서 제거한다. 새 revision은 DB 담당이 지정한 `e2a91d4f6c38_add_service_notices.py`로 만들고 `down_revision = "3f8e1c2a7b90"`을 사용한다.

`content` 최대 길이는 현재 API·Frontend가 사용 중인 **20,000자**로 확정한다. DB migration에는 `CHECK (char_length(content) <= 20000)`을 추가하고 앱의 Pydantic 검증도 동일하게 유지한다.

## DB 변경 설계

### `service.notices`

| 항목 | 수용 내용 |
|---|---|
| PK | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 기본값 | `status DEFAULT 'DRAFT'`, `created_at DEFAULT now()`, `updated_at DEFAULT now()` |
| 상태 제약 | `DRAFT`, `PUBLISHED`, `ARCHIVED`만 허용 |
| 게시 시각 제약 | `DRAFT`는 `published_at IS NULL`, `PUBLISHED`·`ARCHIVED`는 `published_at IS NOT NULL` |
| 본문 제한 | `char_length(content) <= 20000` |
| 인덱스 | `idx_notices_created_by`, `idx_notices_updated_by`, `idx_notices_status_published(status, published_at DESC, id DESC)` |
| 갱신 시각 | `BEFORE UPDATE`에서 `service.trigger_set_updated_at()` 호출 |
| 권한 | DB 관례의 `ALTER DEFAULT PRIVILEGES`를 사용하고, `app_svc`에는 `SELECT`, `INSERT`, `UPDATE`만 유지 |

Alembic `upgrade()`에는 테이블·제약조건·인덱스·`set_updated_at_notices` 트리거를 만들고, `downgrade()`에는 역순으로 트리거·인덱스·테이블을 제거한다. 소유자·시퀀스 권한을 개별 SQL로 설정하지 않는다.

## Backend 변경 설계

### 모델

- `Notice.id`는 `Identity(always=False)`로 선언한다.
- `status`, `created_at`, `updated_at`은 ORM `default`가 아닌 DB `server_default`로 선언한다.
- 인덱스 이름을 DB 관례로 바꾸고 내림차순 목록 인덱스를 모델·migration에 맞춘다.
- `created_at`, `updated_at`은 앱이 직접 넣지 않는다. `flush()` 후 `refresh()`로 DB가 채운 값을 읽는다.

### 상태 전이

| 현재 상태 | 허용 다음 상태 | `published_at` 처리 |
|---|---|---|
| `DRAFT` | `PUBLISHED` | 현재 UTC 시각을 설정 |
| `PUBLISHED` | `ARCHIVED` | 기존 게시 시각 유지 |
| `ARCHIVED` | `PUBLISHED` | 기존 게시 시각 유지 |

- `PUBLISHED → DRAFT`는 허용하지 않는다.
- `DRAFT → ARCHIVED`는 "게시 이력이 없는 보관" 상태를 만들므로 허용하지 않는다.
- 삭제 API는 SQL `DELETE`를 실행하지 않고 `ARCHIVED`로 상태를 변경한다. DB의 `DELETE` 권한 회수와 일치한다.
- 상태 전이 시 `updated_by_employee_id`만 앱이 갱신한다. `updated_at`은 DB 트리거가 갱신한다.

### API 응답

- 공개 목록·상세 API는 계속 `PUBLISHED`만 반환한다.
- 관리자 생성·수정 API는 초안의 `published_at = null`을 유지해야 한다. 현재처럼 `created_at`으로 대체하지 않는다.
- 이를 위해 생성·수정 응답은 `status`, nullable `published_at`, `created_at`, `updated_at`을 포함하는 관리자 응답 모델로 통일한다.
- Frontend는 생성 결과가 `DRAFT`면 관리자 수정 화면으로, `PUBLISHED`면 공개 상세 화면으로 이동한다.

### 페이징

현재 공개 목록의 `page/page_size + total_count` 계약은 유지한다. DB 담당이 제안한 keyset pagination은 대량 공지 운영 시 별도 호환 API 또는 다음 개선 PR로 도입한다. 이번 피드백 수용 PR에서 cursor 계약을 강제 변경하지 않는다.

## DB 담당 확인 필요 사항

피드백의 `ck_notices_published_at_consistent`는 한 행의 현재 값만 검사한다. 앱이 `PUBLISHED → DRAFT`에서 `published_at`까지 `NULL`로 바꾸면 이 CHECK만으로는 과거 게시 이력을 알 수 없다.

따라서 "DB가 PUBLISHED → DRAFT를 반드시 차단"해야 한다면 `set_updated_at_notices`와 별도로 상태 전이 검증 트리거가 필요하다. 이번 구현에서는 앱 서비스가 전이를 차단하고, DB 담당에게 상태 전이 트리거 추가 여부를 확정받는다.

## 구현 순서

1. 수동 SQL 파일과 수동 DDL 중심 문서를 제거·정정한다.
2. `e2a91d4f6c38_add_service_notices.py` Alembic revision을 추가한다.
3. SQLAlchemy 모델을 IDENTITY·서버 기본값·인덱스·FK 선언에 맞춘다.
4. 서비스의 생성·수정·논리 삭제 상태 전이와 응답 모델을 수정한다.
5. 관리자 초안·재게시 흐름에 맞게 Frontend API 타입과 이동 경로를 수정한다.
6. migration upgrade/downgrade, DB 기본값·트리거, 모든 상태 전이, 권한 거부(DELETE)를 테스트한다.
7. Neon 분리 브랜치에서 migration과 CRUD를 검증한 뒤 PR을 갱신한다.

## 완료 기준

- `alembic heads`가 `e2a91d4f6c38` 하나를 가리킨다.
- 빈 값으로 생성해도 DB가 `id`, `DRAFT`, `created_at`, `updated_at`을 채운다.
- `DRAFT → PUBLISHED → ARCHIVED → PUBLISHED`가 성공하고 게시 시각은 유지된다.
- 공개 API는 `PUBLISHED`만, 관리자 API는 모든 상태를 정확한 nullable `published_at`과 함께 반환한다.
- `app_svc`의 SQL `DELETE`는 권한 오류가 나며 API 삭제는 `ARCHIVED` 전환으로 성공한다.
